# 16 大きなファイルのアップロード(生のバイナリ)と、実験詳細の「資料」タブ 計画

状態: **実装済み(ローカルで確認済み)・本番は未反映**。本番への反映は、人の了承を得てから §4 の順で行う。

ローカルの確認(2026-10-18): `npm test` は 103 件中 101 件成功・失敗 0(2 件は条件付きで飛ばすテスト)。`/upload` の試験は、25MB のファイル(base64 の方式では送れなかった大きさ)の往復、上限ちょうど・超過、認証なし、名前なし・不正な %、空のファイル、HTML の種類の扱い、プリフライト。画面は、資料タブでのアップロード(進み具合の表示)・一覧・削除(ゴミ箱に入る)、スマホ幅(375px)で横にはみ出さないことを確認した。**本番でしか確かめられないこと**: Cloudflare の 100MB の制限の実際の値、無料プランの CPU 10ms で大きいファイルを流せるか、Office Online ビューアで大きいパワポが開けるか。

## 1. やりたいこと

- 実験ごとに、発表用のパワポ(と PDF)を置けるようにする。置き場所は、実験詳細ページに新しく作る **「資料」タブ**(人が案 B を選んだ)
- 発表用のパワポは画像や動画で大きくなるので、**アップロードの上限 20MB をなくし、最大 95MB まで**扱えるようにする(人が方式 A を選んだ)
- 置き場所は今までどおり R2(Google Drive・Teams は使わない。人の判断)

## 2. 決まっていること(判断の記録)

| 項目 | 決定 | 理由 |
|---|---|---|
| 置き場所 | R2(`scicomi-portal-files`) | 2026-10-18 時点で 142 件・81.2MB。無料枠 10GB に対して十分余裕がある。Drive は個人アカウント(Workspace でない)で容量の管理が難しく、Teams はサイトと連携できない |
| アップロード方式 | **生のバイナリを `POST /upload` で送り、Worker がそのまま R2 に流す**(方式 A) | 今の「base64 を JSON に入れて送る」方式は、元の約 1.34 倍に膨らみ、本文の上限 28MB(`index.js` の `MAX_REQUEST_BYTES`)と Worker のメモリ(128MB)で 20MB が限界。生のバイナリなら、Worker は中身をメモリに展開せずに R2 へ流せる |
| 上限 | 設定 `file_max_mb` の範囲を 1〜**95** にする。既定値は **10 → 50** | Cloudflare の無料プランは、リクエスト本文が 100MB まで(超えると Worker に届く前に 413)。余裕を見て 95 |
| 画面 | 実験詳細に 4 つ目のタブ「資料」(案 B) | メディアタブの写真・動画と混ざらない |
| 編集 | しない(閲覧は Office Online ビューア、差し替えはダウンロード → 編集 → アップロード) | R2 のファイルは直接編集できない |

## 3. 設計

### 3-1. Worker: `POST /upload`(生のバイナリ)

- 送り方: 本文がファイルそのもの。ヘッダーで次を送る
  - `Authorization: Bearer <一般のトークン>`(トークンを URL に載せない方針は今までどおり)
  - `X-File-Name: <encodeURIComponent(ファイル名)>`(ヘッダーには ASCII しか入らないため)
  - `Content-Type: <ファイルの種類>`(今の `uploadFile` と同じく、`type/subtype` の形だけ受け付ける)
- `Content-Length` が無い・0・上限超えなら、本文を読まずに断る(`length_required` / `invalid_file` / `file_too_large`)
- 本文は `FixedLengthStream` を通して `env.FILES.put` に渡す。宣言した長さと実際の長さが違えば失敗する(R2 は長さの分かるストリームしか受け付けないため、これも兼ねる)
- 返す形は、今の `uploadFile` と同じ `{ success, file: { name, url, driveId, size, uploadedAt } }`。保存データの形は変えない
- CORS: 独自ヘッダーを使うので、ブラウザは事前確認(OPTIONS)を送る。`corsHeaders` の `Access-Control-Allow-Headers` に `Authorization, X-File-Name` を足す
- 監査ログは今と同じ `uploadFile`
- **今の `action: 'uploadFile'`(base64)は残す**。古い画面(キャッシュ)からのアップロードを壊さないため。こちらの上限は、新しい設定値と 20MB の小さいほう(`LEGACY_UPLOAD_MAX_MB`)

### 3-2. フロント: `api.uploadFile(file, { onProgress })`

- 全ページのアップロードを、新しい `POST /upload` に切り替える(イベントの書類・写真・ガイドのファイルも含む。呼び出し側は変えない)
- 進み具合を出すため、`fetch` ではなく `XMLHttpRequest` を使う(`fetch` は送信の進捗を取れない)。`onProgress(送った割合 0〜1)` は省略できる
- タイムアウトは、ファイルの大きさに合わせて伸ばす(120 秒 + 1MB あたり 10 秒)
- 失敗の扱いは `_postOnce` と同じ(通信断は `NETWORK_UNREACHABLE`、`unauthorized` は再ログインの画面)

### 3-3. データ: 実験に `Slides` 列を足す

- `worker/migrations/0010_experiment_slides.sql`: `ALTER TABLE experiments ADD COLUMN Slides TEXT NOT NULL DEFAULT '';`
- 中身は JSON 配列の文字列(`Photos` と同じ形)。1 件は `{ name, url, driveId, size, uploadedAt }`
- `tables.js` の experiments の `columns` に `Slides` を足す(バックアップ・復元・`isFileReferenced` は `columns` から自動で対象になる)
- `data.js` の `TRASH_ITEM_RULES.experiments` に `Slides: { key: fileKey, label: fileLabel }` を足す(資料を消すとゴミ箱に入る)
- 長さの区分は「その他」(100,000 バイト)。1 件 200 バイト前後なので、上限の 30 件でも十分収まる

### 3-4. 画面: 実験詳細の「資料」タブ

- タブ: 「実験情報／振り返り／メディア／**資料**」
- 中身: 「＋ 資料を追加」ボタン、並び順の切り替え(新しい順／古い順。アップロード日時で並べる。選んだ順は端末の `localStorage` の `scicomi_slide_sort` に覚える)、資料の一覧(ファイル名・アップロード日時・大きさ)。ファイル名を押すと新しいタブで開く(`fileOpenUrl` を通すので、パワポは Office Online ビューア、PDF はブラウザで開く)
- 一覧には、ダウンロード・削除のボタンを置かない(人の判断)。各行の ✎ で「名前の変更」のダイアログを開き、削除はそのダイアログの「この資料を削除」から行う
- 名前: ファイルを選ぶと、アップロードの前に名前を確かめて変えられるダイアログが出る。あとからも ✎ で変えられる。変えるのは表示名(`Slides` の `name`)だけで、R2 のファイルと URL は変わらない(ダウンロードしたときのファイル名は元の名前のまま)。拡張子を消しても元の拡張子を付け直す(`normalizeSlideName`。開き方の判定に使うため)。名前の変更はゴミ箱に入らない
- 選べるファイル: `.ppt` `.pptx` `.pdf` `.key` `.odp`(`accept` で絞る。サーバーは種類を制限しない)
- アップロード中は、一覧の上に進み具合(%)を出す
- 件数の上限は 30 件(写真の 15 枚と同じく、保存の直前の最新の記録で判定する)
- 削除は写真と同じ(確認 → ゴミ箱。実体はゴミ箱の完全削除に任せる)。行の特定は位置ではなく `driveId`(無ければ URL)で行う(`slideKey`)
- 実験情報タブの「スライド URL」(`SlidesURL`)は、そのまま残す(外部のリンク用)

### 3-5. 設定ページ

- 「ファイルのアップロード」の欄を足し、`file_max_mb`(1〜95MB)を画面から変えられるようにする(今は画面が無い)

## 4. 本番への反映の順番(§5-B と同じ考え方)

**Worker を先に出す。** 新しい画面が古い Worker に `/upload` を送ると失敗するため。

1. バックアップを取る(AI向けREADME §5-G)
2. `npm run db:migrate:remote`(`experiments` に `Slides` 列が増える。既存データはそのまま)
3. `npm run deploy`(`/upload` と、新しい上限が使えるようになる。古い画面は base64 のまま動く)
4. `git push`(画面が `/upload` を使い始め、資料タブが出る)
5. 本番で、ダミーのパワポ(個人情報なし。20MB 超のものを含む)を上げて、開く・削除する・ゴミ箱から戻す、を確かめる。済んだら人の了承を得てダミーを完全削除する

## 5. 認識しているリスク

- 大きいファイルを置けるので、R2 の無料枠(10GB)に早く近づく。使用量は人が Cloudflare ダッシュボード(R2 → `scicomi-portal-files`)で見る。目安として 8GB を超えたら、上限を下げるか古い資料を整理する
- Office Online ビューアには、ファイルの大きさの上限があるとされる(PowerPoint は数十MB。正確な値は未確認)。超えるとビューアがエラーを出すので、資料タブには「ダウンロード」のリンクも置く
- R2 のファイルは、URL を知っていればログインなしで見られる(今までどおり)。資料に個人情報を入れない
- 無料プランの CPU 10ms の枠: 生のバイナリを流すだけなので、CPU はほぼ使わない(base64 の展開より軽い)。ただし本番では未検証なので、反映後に大きいファイルで確かめる
