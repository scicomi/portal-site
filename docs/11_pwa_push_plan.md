# PWA 化とスマホへのプッシュ通知(計画)

状態: **計画(未実装)**。実装前に「§10 決めること」を人が決める。
版: 1 版(2026-10-11)

## 1. 目的と、完成後の姿

イベントが追加されたときや、新しい情報(ガイド・お知らせ)が載ったときに、**メンバーのスマホに通知が届く**。
通知を押すと、ポータルの該当ページ(イベント詳細など)が開く。

- 外部の有料サービスや通数の上限がある配信サービスは使わない。ブラウザ標準の **Web Push**(Apple・Google・Mozilla の配信基盤。無料・通数の上限なし)を、既存の Cloudflare Worker から直接送る
- ポータルを **PWA**(ホーム画面に追加できるアプリ)にする。iPhone は、ホーム画面に追加したときだけ Web Push を受け取れる(iOS 16.4 以上)ため、PWA 化は必須

### 完成後の使い方(場面ごと)

**場面 1: 通知を受け取れるようにする(メンバー、1 回だけ)**
1. Android: ポータルを Chrome で開き、ホームの「スマホに通知を受け取る」カードの「通知をオンにする」を押す → 許可する。ホーム画面への追加は任意(追加を勧める表示は出す)。
2. iPhone: Safari で開くと、カードに「共有ボタン → ホーム画面に追加 → 追加したアイコンから開いて、通知をオンにする」の手順が出る。ホーム画面のアイコンから開き直して「通知をオンにする」→ 許可する。
3. 以後、アカウントメニューの「通知の設定」で、受け取る種類(イベント追加 / ガイド / お知らせ)の切り替えと、「テスト通知を送る」ができる。

**場面 2: イベントが追加された**
- 誰かがウィザードでイベントを保存すると、数秒〜数分で「新しいイベント: ○○サイエンスショー(11/3)」が届く。押すと `events.html?event=ID` が開く。
- 削除の取り消し(ゴミ箱からの復元・Undo)による再作成では通知しない。

**場面 3: 新しい情報(ガイド・お知らせ)**
- 管理者がガイドを新しく作ったとき、または保存時に「メンバーに通知する」に印を付けたとき、「ガイドが更新されました: 備品の貸し出し手順」が届く。
- 管理者が設定ページの「お知らせを送る」で、題名・本文・開くページを入れて送る(例:「明日の集合時間が 9:00 に変わりました」)。

**場面 4: 卒業・引退した人に届かないようにする**
- 一般パスワードを変えると(年度の切り替え)、それまでの登録はすべて無効になり、新しいパスワードでログインし直した端末だけに届く。

## 2. 前提と制約(調べた結果)

| 項目 | 内容 | この計画への影響 |
|---|---|---|
| iPhone(iOS / iPadOS 16.4 以上) | **ホーム画面に追加した PWA の中でだけ** Web Push を受け取れる。Safari のタブのままでは不可。許可の確認は、ボタンを押した操作の中でしか出せない | PWA 化が必須。iPhone の Safari では「ホーム画面に追加」の案内を出す |
| Android(Chrome など) | ブラウザのままでも受け取れる。ホーム画面への追加は任意 | — |
| PC(Chrome・Edge・Firefox・Safari) | そのまま受け取れる | おまけで使える |
| GitHub Pages | `https://scicomi.github.io/portal-site/` の配下に置く。Service Worker の範囲(scope)は `/portal-site/` | `sw.js` はルート直下(他の HTML と同じ場所)に置く |
| 配信の鍵(VAPID) | 送り主を証明する鍵の組。**秘密鍵は Worker の Secret**、公開鍵は画面に配ってよい | 秘密鍵は人がスクリプトで作って登録する(§8)。AI は値を見ない |
| Cloudflare 無料枠 | 1 回の実行で CPU 10ms、外部への `fetch` は 50 回まで(`waitUntil` の中も同じ枠) | 端末ごとの暗号化と送信を、1 回にまとめて全員へ送ると枠を超えうる。**送信待ちの表(outbox)に入れ、少しずつ送る**(§5-3) |
| 既存の認証 | 共通パスワード方式。トークンは 180 日有効、パスワード変更で即失効(epoch) | 登録には一般のトークンを必要にし、登録時の epoch を一緒に記録する |
| LINE 通知 | 削除済み(月 200 通の上限にすぐ達するため。§11) | 置き換え先がこの機能 |

## 3. 方針(大きな決定)

1. **Web Push を Worker から直接送る。** 外部の配信サービス(OneSignal、Firebase の管理画面など)は使わない。アカウントの引き継ぎ対象を増やさないため、また通知の内容を第三者のサービスに預けないため。
2. **暗号化と署名は自前で実装する(`worker/src/webpush.js`)。** Worker 標準の WebCrypto で書ける(ECDH P-256・HKDF・AES-128-GCM・ES256)。npm の依存を増やさない(現在、Worker の実行時の依存は 0)。RFC 8291 の付録にある試験用の値で、正しく暗号化できることをテストで確かめる。
3. **通知の中身は最小限にする。** ロック画面に出るため、個人情報(氏名・連絡先)は載せない。イベントは「題名と日付」だけ(場所は §10 で決める)。中身は端末までの間で暗号化されるので、Apple・Google には読めない。
4. **登録は端末ごと。** 個人認証が無いので、「誰の端末か」は必須にしない(アカウントメニューの「あなたの名前」が設定されていれば、メンバー ID を添えるだけ)。
5. **オフライン対応(画面のキャッシュ)はしない。** `sw.js` に `fetch` の処理を置かない。`git push` した新しい画面がすぐ反映される今の動きを変えないため。データのキャッシュは今までどおり `api.js` の localStorage。
6. **送信は「送信待ちの表」を経由する。** 保存の処理の中では、送信待ちに積んで最初の数件だけ送る。残りは 1 分ごとの定期実行が送る。無料枠の CPU・`fetch` の上限に収まり、配信サービスが一時的に失敗しても再送できる。

## 4. 全体の流れ

```
【登録】
 スマホ(PWA)                         GitHub Pages                     Cloudflare Worker / D1
  ├ sw.js を登録 ───────────────────▶ /portal-site/sw.js
  ├ 「通知をオンにする」→ 許可
  ├ pushManager.subscribe(公開鍵) ─▶ Apple / Google の配信基盤 ─▶ 宛先(endpoint)と鍵を返す
  └ api.pushSubscribe(endpoint, 鍵, 種類) ────────────────────────▶ push_subscriptions に保存

【送信】
 イベントを保存(save, 新規) ─▶ Worker ─▶ push_outbox に「誰に・何を」を積む
                                  └ waitUntil で最初の数件を送る
 1 分ごとの定期実行 ─────────▶ Worker ─▶ 残りを送る(失敗は再送、404/410 の宛先は削除)
                                  │  暗号化(RFC 8291)+ 署名(VAPID)して POST
                                  ▼
                        Apple / Google / Mozilla の配信基盤 ─▶ スマホの sw.js の push イベント
                                                                  └ 通知を表示 → 押すとページを開く
```

## 5. バックエンド(Worker)の設計

### 5-1. テーブル(マイグレーション `0006_push.sql`。番号は実装時に `ls worker/migrations` の最後 + 1)

`push_subscriptions`(端末ごとの登録)

| 列 | 内容 |
|---|---|
| `Endpoint` | 主キー。配信基盤の宛先 URL(秘密に近い扱い。API では返さない) |
| `P256dh` / `Auth` | 端末の公開鍵と認証用の値(暗号化に使う) |
| `Topics` | 受け取る種類の JSON 配列(`["events","guides","notice"]`) |
| `MemberID` | 「あなたの名前」が設定されていればそのメンバー ID。無ければ空 |
| `Epoch` | 登録したときの一般トークンの epoch。現在の epoch と違えば送らない(パスワード変更で全員の登録が無効になる) |
| `Label` | 端末の目安(「iPhone」「Android」など。User-Agent から粗く作る。詳細は保存しない) |
| `FailCount` | 連続で失敗した回数。一定回数で削除 |
| `CreatedAt` / `LastSeenAt` | 登録日 / 最後に画面から登録を確認した日 |

`push_outbox`(送信待ち)

| 列 | 内容 |
|---|---|
| `ID` | 連番 |
| `Endpoint` | 宛先 |
| `Payload` | 通知の中身の JSON(`{title, body, url, tag}`) |
| `Attempts` / `NextAt` | 試行回数 / 次に送ってよい時刻(失敗時は間を空けて再送) |
| `CreatedAt` | 積んだ時刻。1 日たっても送れないものは捨てる |

- **どちらも `tables.js` の `RESOURCES` には入れない**(汎用の list/save で読めないようにする。宛先を画面に返さないため)
- **毎日のバックアップ(`BACKUP_TABLES`)にも入れない。** 復元しても、端末が次に画面を開いたときに自動で登録し直す(§6-3)ので、失っても困らない。宛先の URL を R2 に残さないため

### 5-2. API(`index.js` に action を追加)

| action | 権限 | 内容 |
|---|---|---|
| `pushSubscribe` | 一般のトークン | 宛先・鍵・種類・メンバー ID を登録(同じ宛先なら上書き)。`Epoch` と `LastSeenAt` を更新。宛先の URL は、既知の配信基盤のホストだけを受け付ける(下記) |
| `pushUnsubscribe` | 宛先を知っていること | 登録を消す(ログアウト時・通知オフ時) |
| `pushTest` | 一般のトークン | 自分の宛先 1 件だけにテスト通知を送る(1 端末 1 分に 1 回まで) |
| `pushStats` | 管理者 | 登録台数(種類別)だけを返す。宛先は返さない |
| `pushBroadcast` | 管理者 | お知らせを送る(題名 100 文字・本文 300 文字まで。開くページはサイト内のパスだけ) |

- **宛先 URL の検査**: Worker が利用者から受け取った URL へ POST するので、任意の URL を許すと踏み台にされうる。`https://` で、ホストが `fcm.googleapis.com`、`*.push.apple.com`、`updates.push.services.mozilla.com`、`*.notify.windows.com` のいずれかのものだけを受け付ける。ローカルの結合テスト用に、`.dev.vars` で `PUSH_ALLOW_LOCAL_ENDPOINT=true` のときだけ `http://127.0.0.1` を許す
- 監査ログ: `pushSubscribe` は記録しない(数が多くなるため)。`pushBroadcast` は `push_broadcast`、送信の集計は `push_send`(送信 n 件・失敗 m 件・削除 k 件)、送信処理そのものの失敗は `push_fail`

### 5-3. 送信の処理(`worker/src/push.js` と `webpush.js`)

- `enqueuePush(env, topic, payload)`: 種類(topic)を受け取る登録のうち、`Epoch` が現在のものだけを `push_outbox` に積む
- `drainPushOutbox(env, limit)`: `NextAt` が来たものを `limit` 件取り出して送る
  - 応答 201: 送信待ちから消し、`FailCount` を 0 に
  - 404 / 410(端末側で解除された): 登録ごと消す
  - 429 / 5xx: `Attempts` を増やし、`NextAt` を 1・5・30 分後にずらす。5 回で諦める
  - 413 / 400(中身が不正): その 1 件を捨て、`push_fail` に記録
- VAPID の署名(JWT)は、配信基盤のホストごとに 1 つ作って 12 時間使い回す(`kv_cache` テーブルに置く)。署名の回数を減らして CPU を節約する
- 呼び出し元:
  - `save` の新規イベント(`index.js`): `enqueuePush` → `ctx.waitUntil(drainPushOutbox(env, 少数))`。削除の取り消しによる再作成(`CreatedAt` を持って来る保存)は対象外
  - `save` のガイド: 新規作成のとき、または本文と一緒に `notify: true` が送られたとき(管理者のみ)
  - `pushBroadcast`
  - 定期実行(`scheduled`): 1 分ごとの cron で `drainPushOutbox`。送信待ちが空なら D1 を 1 回読むだけで終わる
- 1 回で送る件数(`limit`)は、§9 のフェーズ 1 で CPU 時間を実測して決める(目安 10 件。無料枠の `fetch` 50 回にも余裕を持たせる)
- 同じイベントの通知が重ならないよう、通知に `tag`(例 `ev_xxx`)を付ける。端末側で同じ tag は上書き表示になる

### 5-4. 設定(`worker/src/config.js` の `DEFAULT_CONFIG`)

| キー | 既定 | 内容 |
|---|---|---|
| `push_events_enabled` | `true` | イベント追加で自動送信する |
| `push_guides_enabled` | `true` | ガイドの新規作成で自動送信する |
| `push_event_location` | `false` | イベント通知に場所を載せるか(§10) |

- 公開鍵は `wrangler.toml` の `[vars]` に `VAPID_PUBLIC_KEY` と `VAPID_SUBJECT`(連絡先。`mailto:` の共有メール)として置き、`getPublicConfig` で画面に渡す。1 か所で管理し、`config.js`(フロント)には書かない
- 秘密鍵は Secret の `VAPID_PRIVATE_KEY`(`wrangler secret put`。人が行う)。未設定なら送信処理は何もせず、`pushSubscribe` は `feature_disabled` を返す

### 5-5. 定期実行

- `wrangler.toml` の `crons` に `"* * * * *"`(1 分ごと)を追加。`scheduled` で `event.cron` を見て、毎日 03:00 の処理と送信を分ける
- 毎日 03:00 の `runMaintenance` に追加: 1 日以上残っている送信待ちの削除、`LastSeenAt` が 180 日より前(トークンの有効期間)の登録の削除、`Epoch` が古い登録の削除

## 6. フロント(GitHub Pages)の設計

### 6-1. 追加するファイル(ルート直下)

| ファイル | 内容 |
|---|---|
| `manifest.webmanifest` | 名前「SciComi Site」、短い名前「SciComi」、`start_url: "./index.html"`、`scope: "./"`、`display: "standalone"`、`theme_color` / `background_color`(`style.css` の `--primary-color` のライト側 `#464775` と背景色)、アイコン |
| `icons/icon-192.png` / `icon-512.png` / `icon-maskable-512.png` / `apple-touch-icon.png`(180) | 今の `icon.png` は 256px なので、512px の元画像が必要(§10)。maskable は周囲に余白を足したもの |
| `sw.js` | Service Worker。`push`(通知の表示)、`notificationclick`(開いているタブがあれば前に出して移動、無ければ開く)、`pushsubscriptionchange`(宛先が変わったら登録し直す)だけ。**`fetch` の処理は置かない**(§3-5) |
| `pwa.js` | 共通の処理: Service Worker の登録、通知の状態の判定、オン・オフ、登録の再送、通知の設定のモーダル |

- `sw.js` で開くページは、通知の `url` がこのサイト内の相対パス(`events.html?event=...` など)のときだけ。外部の URL は開かない
- `pushsubscriptionchange` は画面のトークンを持たないので、Worker 側は「古い宛先が登録済みなら新しい宛先へ付け替える」action(`pushResubscribe`)で受ける

### 6-2. すべての HTML の `<head>` に追加(10 ページ)

```html
<link rel="manifest" href="manifest.webmanifest">
<meta name="theme-color" content="#464775">
<link rel="apple-touch-icon" href="icons/apple-touch-icon.png">
```

スクリプトは `config.js → api.js → app.js → pwa.js → 各ページ.js` の順(既存の順番は変えず、`app.js` の後ろに足す)。

### 6-3. 動き

- どのページでも、ログイン後に `pwa.js` が Service Worker を登録する
- 通知が許可済みで登録もある端末は、1 日 1 回 `pushSubscribe` を送り直す(`LastSeenAt` と `Epoch` を新しくする。パスワード変更後に再ログインした端末は、これで自動的に復活する。DB を復元したときも同じ)
- 「通知をオンにする」: ボタンの操作の中で `Notification.requestPermission()` → `subscribe` → `api.pushSubscribe`。拒否されたら「端末の設定から通知を許可してください」の案内を出す
- iPhone で、ホーム画面のアイコンから開いていない(`display-mode: standalone` でない)ときは、ボタンの代わりに「ホーム画面に追加」の手順を出す
- ログアウト: 端末の登録を解除してから(`pushUnsubscribe` と `unsubscribe()`)ログアウトする
- 失敗の文言は `humanizeApiError(e)` を通す(既存のルール)

### 6-4. 画面の変更

- **ホーム**(`index.html` / `home.js`): 未登録の端末だけに「スマホに通知を受け取る」カード
- **アカウントメニュー**(`app.js` の `renderHeader`): 「通知: オン / オフ」→ 通知の設定のモーダル(種類の切り替え・テスト通知)
- **ガイド**(`guide.js`): 管理者の保存ボタンの横に「メンバーに通知する」(新規作成のときは最初から印が付いている)
- **設定ページ**(`settings.html` / `settings.js`): 「プッシュ通知」の区画(登録台数、自動送信の切り替え、お知らせを送る)
- アクセシビリティは既存の共通の仕組みに合わせる(モーダルのラベル、トグルの `aria-checked`、タップ領域 44px)

## 7. セキュリティ・個人情報

| 心配 | 対策 |
|---|---|
| 退会・卒業した人に届き続ける | 登録に epoch を記録し、一般パスワードの変更で全員分が無効になる。ログアウトで解除。180 日見ていない端末は削除 |
| ロック画面から内容が漏れる | 題名と日付だけ。氏名・連絡先・住所は載せない。お知らせの本文は管理者が書くので、設定ページに「個人情報を書かない」の注意を出す |
| 宛先 URL の悪用(他人の端末に送る・踏み台) | 宛先は API で返さない。受け付けるホストを配信基盤に限る。`pushTest` は自分の宛先だけ・回数制限あり |
| 秘密鍵の漏えい | Secret に置き、バックアップにも出力にも含めない。漏れたら鍵を作り直す(全員の登録がやり直しになる) |
| 通知の連打 | イベントは新規作成のときだけ。ガイドは印を付けたときだけ。お知らせは管理者だけ |

## 8. 鍵の作成と登録(人が行う作業)

`worker/scripts/gen-vapid.mjs` を追加する。鍵の組を作り、**秘密鍵は画面に出さずに** `wrangler secret put VAPID_PRIVATE_KEY` へ直接渡し、公開鍵だけを表示する。

```bash
cd worker
node scripts/gen-vapid.mjs --remote
```

表示された公開鍵を `wrangler.toml` の `VAPID_PUBLIC_KEY` に書いて、デプロイする(公開鍵は秘密ではないので、AI が書いてよい)。

- ローカル用は `node scripts/gen-vapid.mjs --local`(`.dev.vars` に書き込む。本番と同じ鍵を使わない)
- 鍵を作り直すと、全端末の登録が無効になる(端末が次に画面を開いたとき、自動で登録し直す。iPhone は許可が残っていれば操作は不要)

## 10. 決めたこと・残りの確認

### 決定済み(2026-10-11)

1. **通知する条件**: すべての種類のイベント(通常のイベント・その他・全体ミーティング・幹部ミーティング)について、**追加されたとき**と、**既存の内容が編集されたとき**。ガイドやお知らせの通知は、この計画の範囲に含めるかを §10-残り で確認する
2. **イベント通知に場所を載せる**(`push_event_location` の既定は `true`)
3. **日時や場所の変更も通知する**

### 編集の通知の扱い(案。実装時に確定)

出欠の回答、振り返り、添付ファイル、書類の状態の更新など、毎回通知すると多すぎる保存もある。通知する編集は、**題名・日付・終了日・開始/終了時刻・集合/解散時刻・場所**が変わったときに絞る(備考なども含めたい場合は、対象の列を足す)。通知文には変わった項目を書く(例:「日程が変わりました: ○○ 11/3 → 11/10」)。
同じイベントの通知は、`tag` を同じにして端末側で上書きし、10 分以内の連続した編集は 1 件にまとめる(ウィザードで何度も保存しても通知が連打されない)。

### 残りの確認

1. **アイコンの元画像(512×512 以上)**: 下の「用意の仕方」を参照
2. **配信の連絡先(`VAPID_SUBJECT`)**: 共有のメール(`mailto:sc.tokai@gmail.com` など)でよいか
3. **1 分ごとの定期実行**: 足してよいか(説明は下)
4. **ガイドの新規作成・管理者のお知らせも通知するか**: §1 の場面 3 の案のまま入れるか、イベントだけにするか

### アイコンの用意の仕方

- 今の `icon.png` の元データ(Illustrator・Canva・Figma などのファイル、または SVG)があれば、**512×512 か 1024×1024 の PNG で書き出す**のが一番きれい
- 元データが無いときは、256px の画像を拡大して仮に使える(ぼやけるが動く)。後から差し替えれば、全員の端末に自動で反映される
- 余白: 端末によって角が丸く切り取られるので、図柄は中央の約 80% に収め、背景は単色で四隅まで塗る(maskable 用)
- 画像の用意ができない場合は、AI が `icon.png` から仮の 512px と maskable 版を作る(フェーズ 2)

### 配信の連絡先メール(`VAPID_SUBJECT`)

通知を送るとき、Worker は「この送信元はこういう団体です」という署名に連絡先を 1 つ添える(Web Push の仕様 VAPID)。Apple・Google の配信基盤が、**送り方に問題があったとき(大量送信など)に運営者へ連絡するため**のもの。メンバーの画面には出ず、メールが日常的に届くわけでもない。共有メールで十分。

### 1 分ごとの定期実行

Cloudflare の Cron Trigger を 1 分ごとに動かす設定。今は毎日 03:00 のバックアップだけが動いている。通知は、保存の瞬間に「送信待ち」の表に積み、**この定期実行が 1 分以内に、残りの端末へ順番に送る**。
- 理由: 無料枠では 1 回の実行で外部へ送れるのが 50 回までで、端末が 50 台を超える、または配信基盤が一時的に失敗したときに、保存の処理の中だけでは全員に届かない
- 送信待ちが空のときは何もせず終わる。実行は 1 日 1,440 回で、無料枠(1 日 10 万リクエスト)の約 1.4%
- 足さない場合: 保存の処理の中で送れる分(約 40 台まで)だけになり、失敗の再送もできない

## 11. LINE 通知の削除(実施済み、2026-10-11)

LINE 公式アカウントによる新規イベント通知は、**送れる通数の上限が月 200 通**で、メンバー全員に一斉送信すると少ない回数の配信で上限に達する見込みだったため、実装を断念して削除した(ブロードキャスト配信は友だちの人数分が通数として数えられる)。

- コード: `worker/src/line.js` を削除し、`index.js` の呼び出し、`config.js` の `line_channel_access_token` / `line_add_friend_url` / `event_notify_enabled`、設定ページの「LINE通知」、ホームの「友だち追加」カードを削除
- 文書: README・AI向けREADME・人への引き継ぎ・docs/08 から記述を削除
- **本番に残っているもの(人が判断して片付ける)**:
  - D1 の `secrets` に `secret_line_channel_access_token`、`config` に `line_add_friend_url` / `event_notify_enabled` の行が残っている可能性がある。新しいコードは読まないので害はないが、消すならバックアップ後に D1 Console で消す
  - LINE Developers のチャネル・公式アカウントは、不要なら人が LINE 側で停止・削除する(トークンの失効を含む)
